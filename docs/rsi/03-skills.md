# 技能自进化（Skill Self-Evolution）专题：按"优化什么 / 怎么优化 / 什么场景"逐篇梳理

> 2026-10 ｜ 配套：[`01-survey.md`](01-survey.md)（RSI 主报告）、[`02-papers.md`](02-papers.md)（文献清单）
>
> **统一用三个问题看每一项工作**：
> **① 优化什么** —— 具体动的是 `name` / `description` / `SKILL.md` 正文 / 脚本与参考文件 / 整个技能库 / 还是"改进流程"本身？
> **② 怎么优化的、优化前后有没有对比** —— 机制一句话 + 论文里给出的前后数字。
> **③ 什么场景、用什么数据集** —— 任务类型与基准名。
>
> 中文名与元数据对应关系（以 VCE-Skill 与 Selm 的形式化为例，两篇都把技能拆成字段）：
> `s = (name, description, instruction_content, trigger_conditions, task_category)`（Selm）；
> `s = ⟨m, C_s⟩`，其中 `m` 是 YAML frontmatter 的 `name`+`description`，`C_s` 是正文指令与可选脚本/参考/配置（VCE-Skill）。

## 1. SkillOpt：把单份技能文档当作"可训练参数"

*Yang et al.（Microsoft / SJTU 等），2026-05，[arXiv:2605.23904](https://arxiv.org/abs/2605.23904)*

**① 优化什么**
一份技能文档（部署产物是 `best_skill.md`，约 **300–2,000 tokens**）。编辑是**有界的增/删/改**：patch 模式做 append / insert / replace / delete，rewrite 模式才对整份文档重写。论文把技能定义为"插进上下文的自然语言策略"，**没有把 name/description 单列为优化对象**；另有"受保护的 slow-update 字段"，step 级编辑不能覆盖它。

**② 怎么优化**

> 一句话：把"改技能"做成一次**受控的文本梯度下降**——证据是 rollout 批次，步长是编辑预算，验证集是验收门。

**每轮流程（7 步）**

1. **前向：收集证据。** 冻结的目标模型在当前技能下跑一个 rollout batch，记录任务元数据、消息、工具调用、观察、命令输出、最终答案、验证器反馈，以及基准特有上下文（表格预览、文档引用、执行轨迹）。这一批轨迹就是本轮唯一的证据单元——批次小则更新快但噪声大，批次大则能看到更多可复用的模式。
2. **反向：分 minibatch 反思。** 优化器模型（另一个前沿模型）先把**失败与成功分开**，各自再切成反思 minibatch。理由是单条轨迹容易产出"个例补丁"，只有 minibatch 才能暴露**可复用的过程性错误**（比如总是搜错来源、答案格式不对、没有校验工具返回结果）。失败组提出"补上缺失的规则 / 纠正错误规则"，成功组提出"保留并固化已经有效的做法"。每条反思返回的是**结构化的增/删/改编辑**（在 rewrite 模式下是少量重写建议）。实际配置是 **16 个 analyst worker 并行**出提案，每个 minibatch 允许**最多 3 轮教师自反思**精修。
3. **分层合并。** 先分别合并"失败驱动"和"成功驱动"的编辑，再把两组合到一起，**失败修正优先级更高**。这一步负责滤掉重复的、互相矛盾的、以及只对某个具体样例成立的建议。
4. **限幅更新（文本学习率）。** 优化器模型把合并后的编辑池按**预期效用排序**，截断到前 `L_t` 条——`L_t` 是第 t 步允许施加的最大编辑数，也就是"文本学习率"。支持 constant / linear / cosine / autonomous 四种调度，**默认 cosine**（先大步快速接近，再小步做整合）。编辑在 patch 模式下是位置化的 append / insert / replace / delete，在 rewrite 模式下才触发整篇重写。**step 级编辑不允许覆盖被保护的 slow-update 字段**，保证快更新与慢沉淀不互相污染。
5. **验收门。** 候选技能在 **selection split（`D_sel`）** 上用**同一个冻结模型 + 同一个 harness** 重新评测：分数高于当前技能 → 成为新的当前技能；同时超过历史最佳 → 导出为 `best_skill.md`；否则**拒绝**。训练集只提供经验，验证集只负责门控，测试集只用于最终汇报，三者不混。
6. **负反馈。** 被拒的编辑连同"它造成多少分下降"一起写进 epoch 内的 **rejected-edit buffer**，后续同 epoch 的反思调用会读到它，从而避免重复踩同一个坑。这一步**不增加任何推理时开销**（只在训练期起作用）。
7. **慢更新（动量项）。** 从第 2 个 epoch 起，在 epoch 末用 **20 个采样任务**对比"上一 epoch 的技能 vs 当前技能"，由优化器模型把跨步稳定的规律写进**受保护段**（`SLOW_UPDATE_START/END`，step 级编辑碰不到它），这段改动本身也要过同一道门控；此外还会更新一份 **meta skill**——它只进 teacher 的提示、**不随技能一起部署**。

**关键参数**

| 参数 | 含义 | 论文取值 |
|---|---|---|
| 训练轮次 | epoch 数 | **4** |
| rollout batch | 每步的证据量 | **40 条 / step** |
| 反思 minibatch | 每次反思消化的轨迹数 | **8**；**16 个 analyst** 并行；≤3 轮教师自反思 |
| `L_t` | 每步允许的编辑数（文本学习率） | **4**，cosine 衰减到下限 **2**（也可 constant / linear / autonomous） |
| slow update | 每个 epoch 末的对比样本量 | **20 个任务** |
| 数据划分 | train : selection : test | **2 : 1 : 7** |
| 被接受的编辑总数 | 收敛所需步数 | 1–44 次 |
| 部署产物大小 | `best_skill.md` | 300–2,000 tokens |
| 推理时额外调用 | 部署后开销 | **0** |

**门控的精确写法**：`score_cand > score_cur`（**严格大于，平局即拒绝**）才替换当前技能；再满足 `score_cand > score_best` 才写出 `best_skill.md`。哈希命中缓存时直接复用分数，不重复评测。个别基准有例外配置：LiveMath 用 35 items/epoch、batch 200；ALFWorld 为 39 train / 140 selection / 134 test。

**为什么这么设计（论文的论证）**：无界重写会抹掉有用规则、引入互相冲突的指令、或对某个局部失败过拟合，所以必须限幅；"看起来合理的文本诊断"落到真实目标模型上完全可能反而降分，所以必须留出验证门；而被拒的编辑本身携带信息，浪费掉可惜，所以留作负反馈。这三点正是它和"随手让模型改提示"的分水岭。

**优化前后对比**（GPT-5.5 直连对话，同表内还有 5 个技能来源做对照）

| 基准 | 无技能 | SkillOpt | 增益 |
|---|---|---|---|
| SearchQA | 77.7 | 87.3 | +9.6 |
| SpreadsheetBench | 41.8 | 80.7 | +38.9 |
| OfficeQA | 33.1 | 72.1 | +39.0 |
| DocVQA | 78.8 | 91.2 | +12.4 |
| LiveMathematicianBench | 37.6 | 66.9 | +29.3 |
| ALFWorld | 83.6 | 95.5 | +11.9 |

同表里还有 5 个对照技能来源（Human skill / one-shot LLM skill / Trace2Skill / TextGrad / GEPA），SkillOpt 全部胜出；平均 **+23.5pp**，比"逐格最强 baseline"平均再高 **+5.4pp**。Codex 内 **+24.8**、Claude Code 内 **+19.1**；52 个 (模型×基准×执行环境) 单元里**全部最优或并列**。

**③ 场景与数据集**
6 个基准：SearchQA（检索问答）、SpreadsheetBench（表格）、OfficeQA、DocVQA（文档）、LiveMathematicianBench（数学）、ALFWorld（具身决策）；7 个目标模型（GPT-5.5 / 5.4 / 5.4-mini … Qwen 系列）；3 种执行方式（直连对话、Codex、Claude Code）。迁移实验：跨模型规模、跨 Codex↔Claude Code、跨到 Omni-MATH。

## 2. SkillBoost：把技能拆成"组件坐标"，只改该改的那一维

*Lin et al.（浙江大学 / 阿里），2026-07，[arXiv:2607.26643](https://arxiv.org/abs/2607.26643)*

**① 优化什么**
把技能表示成**结构化状态向量，坐标对应关键组件：Metadata、Workflow、Constraints、References**。每次编辑必须指定「操作类型 + 目标组件 + 内容」，且只动被归因的那个组件，其余保持不变。→ **Metadata 是被显式列出的可编辑组件之一**，也就是 name/description 所在的那一层；论文附录还专门分析了 "SKILL.md 格式结构" 的影响。

**② 怎么优化**

> 一句话：把"改技能"写成**受限搜索**——先定位该改哪个组件，再在同一份诊断下换 N 种修法，最后只收"修好的比弄坏的多"的候选。

**先把问题写成 MDP**：state = 当前技能（结构化状态向量），action = 对某个组件的编辑，transition = 确定性应用编辑，reward = 性能变化。于是"自进化"就等于每轮在一个**受限动作空间**里做一次搜索。

**每轮流程（5 步）**

1. **前向 rollout。** 冻结 agent 在 `s_t` 下跑一批任务，逐条记录 step 级轨迹（`(观察, 工具调用, 工具输出)` 三元组序列）与最终答案；成功与失败两类都留着——失败用于归因，成功用于核对"有没有把好的弄坏"。
2. **诊断：把失败定位到组件（Structured Exploitation）。** 只对失败样本做三项检查：
   - **workflow 合规性**：把三种轨迹形态映射到三种缺陷——**跳步**说明过程约束太弱；**按流程走却答错**说明指令歧义；**结论不被观察/工具输出支撑**说明技能没强制"证据落地"。
   - **推理链回溯**：从最终输出倒着走，找**第一个偏离预期规则的步 `j*`**，判断那条规则是"被绕过"还是"根本没走到"——这决定该加约束还是该补说明。
   - **根因聚类**：把同一缺陷的失败并成一组，**一次编辑修一组**；同时把根因分成**策略缺陷**（能靠改技能修）与**能力缺口**（跨版本反复出现、改规则也没用），后者直接排除，避免白改。
   产物是一张 `(原因 → 目标组件)` 清单，把后续编辑**锁在被归因的组件**上，其余部分保持不动。
3. **候选生成（Prior-guided Exploration）。** 诊断固定，只换修复策略 `π`：每套策略决定"改动范围多大"和"先修哪个错"，各产出一个候选，共 **N 个（Best-of-N）**。换策略而不换诊断，是为了让所有候选都基于同一个真实失败，只在"怎么修"上分叉。
4. **两阶段评估。** 全量评估很贵，所以分两步：**Phase A** 把 N 个候选**都只放在"上一轮失败集 F"**（典型 5–30 例）上评；**Phase B** 只把前 **K=2** 名放到完整验证集上全评。这样把贵的评估次数压到常数级。
5. **验收（Verified Acceptance）。** 对每个候选算三项：`gain = Eval(s') − Eval(s_t)`、`Fix`（原来错→现在对的比例）、`Regress`（原来对→现在错的比例）。接受条件是 **`gain > 0` 且 `Regress < ε`**；由于案例按 0/1 计分，`gain ∝ Fix − Regress`，所以这条门控的直白含义就是 **"修好的必须多于弄坏的"**，不管它一共修了多少失败。在通过门控的候选里取 `gain` 最大者；**一个都没通过，技能原地不动**。
6. **进入下一轮。** 被接受的技能成为 `s_{t+1}`，重新 rollout。因为每轮只动被归因的组件，改动始终可追溯。

**理论支撑（为什么别把 N 堆很大）**：在候选从 `ε`-邻域独立采样的假设下，期望方向进展 ≈ `ε√(2lnN/d)`，首达时间下界 ≈ `((ℓ−η)/ε)·√(d/(2lnN))`。也就是说 **N 的收益只随 `√lnN` 增长，而每轮评估成本随 N 线性增长**——这就是"堆候选"不划算的定量解释。

**关键参数**

| 参数 | 含义 | 论文取值 |
|---|---|---|
| N | 每轮候选数（Best-of-N 池） | **4**；消融 1/2/4/6/8，**N=8 只再涨 +2.5pp（Spreadsheet）、+1.1pp（ALFWorld）** |
| K | 进完整验证集的候选数 | **2** |
| F | Phase A 用的失败集规模 | 典型 **5–30 例** |
| guard samples | 守卫样本数 | **10–20** |
| ε | 允许的回归上限 | 只给了符号，**未给数值** |
| T | 迭代轮数 | **未给**（Fig.1 展示了 6 个技能版本） |
| 每轮 rollout | 覆盖范围 | **整个数据集 D**（不是采样 batch） |
| 可编辑维度 | 组件坐标 | Metadata / Workflow / Constraints / References |
| 推理设置 | — | 温度 0.1、max output 16,384、thinking 关闭、seed 42、max ReAct 10、max env steps 50、codegen turns 6 |
| 是否改权重 | — | **否**（模型冻结） |

**为什么这么设计**：两种错误都很贵——只盯当前 batch 会"过拟合 batch"（论文称之为 *skill overfitting*，泛化差距被拉大），无约束探索又会把原本正确的行为改坏。所以它把"改哪里"（诊断）与"怎么改"（策略）拆成两个正交变量，再用带回归上限的门控把它们合起来。与 SkillOpt 恰好互补：**SkillOpt 限的是"改多少"（编辑预算），SkillBoost 限的是"改哪里"（组件 + 回归上限）**。

**优化前后对比**：摘要口径为 23 个 (模型×基准) 配置 SOTA、胜过人工与 LLM 生成的技能、**test–train 差距接近 0**、六个技能版本稳步提升。正文表 I 开头（Claude-opus-4-6）可见无技能/人工/LLM 三行基线：

| 基准（Claude-opus-4-6） | 无技能 | 人工技能 | LLM 技能 |
|---|---|---|---|
| Spreadsheet | 50.0 | 72.5 (+22.5) | 75.0 (+25.0) |
| BFCL-v4 | 27.1 | 26.5 (−0.6) | 28.3 (+1.2) |
| LiveMath | 28.6 | 37.8 (+9.2) | 44.1 (+15.5) |
| ALFWorld | 80.6 | 82.2 (+1.6) | …（截断） |

（SkillBoost 自己的那一行在抓取时被截断，未取到具体值，故不写。）

**③ 场景与数据集**
单轮推理 + 多轮 agentic：Spreadsheet、BFCL-v4（函数调用）、LiveMath、ALFWorld；共 23 个模型—基准配置，模型含 Claude Opus 4.6、Qwen3.5-27B 等。迁移实验测"技能能否被别的 agent 复用"。

## 3. VCE-Skill：用"别人改技能的历史"当先验

*Chen et al.（中科院软件所等），2026-08，[arXiv:2608.16544](https://arxiv.org/abs/2608.16544)*

**① 优化什么**
整个技能包 `s = ⟨m, C_s⟩`：`m` 是 YAML frontmatter 元数据（**required 的 `name` 与 `description`**），`C_s` 是组件集合——`SKILL.md` 正文（instructions，必选）+ 可选的 scripts / references / configs / templates。它不改技能结构定义，而是在"由轨迹驱动的修订提案"之外，再加一路**来自公共版本历史的外部先验**。

**② 怎么优化**

> 一句话：**在"改技能"这件事上开两个信息源**——轨迹告诉你"这次哪里错了"，公共版本历史告诉你"别人改这类技能时通常怎么改"，再按实际效果自动调整该听谁的。

**每轮 8 步（第 0 步是离线的一次性蒸馏）**

0. **离线蒸馏（只做一次）**：相邻版本 diff → 更新事件 `u_j = ⟨raw diff, 涉及组件, 语义操作, 意图⟩` → 按组件/操作/意图分组并**剥离仓库特定细节** → *update pattern* → *skill insight* → *domain insight*，汇成经验库 `B`。→ 关键在"剥离实现细节"：原始 diff 太细、太仓库特定，不抽象就无法跨技能复用。
1. **构造选择上下文**：`z_t = Context(任务, 当前技能 S_{t−1}, 上轮反馈 f_{t−1})`（第一轮没有 `f`）。
2. **选经验**：LLM selector 从 `B` 里选 **≤K 条（允许选 0 条）**，聚合成外部指导 `p^exp_t`。
3. **并行的自我提案**：基础 evolver（EvoSkill / SkillClaw / SkillOpt 任一）只看当前技能与轨迹 `τ_{t−1}`，出 `p^self_t`。
4. **打标签后融合**：每条编辑标 `EXP-k` / `SELF-k`；LLM fuser 按 `λ_exp`、`λ_self` 融合。注意这两个权重**只作冲突时的偏好**，不是配额、也不是概率。
5. **统一改写**：共享 rewriter 对整份技能做 full-skill rewrite（保留 `SLOW_UPDATE` 受保护块）→ `Ŝ_t`。
6. **基础 evolver 决定去留**：`Retain(S_{t−1}, Ŝ_t)`，再用 `S_t` 执行得到 `τ_t`。
7. **归因**：把实际 diff 与带标签的编辑对齐——外部支持且被实现记 `+1`、自提议被实现记 `−1`、未实现或混合记 `0`，均值即 `f^S`；验证反馈 `Δ^V > 0 → f^V = +1`，否则 `−1`；两者相乘得 `f_t = f^V · f^S`。
8. **调注意力**：`λ_exp ← clip(λ_exp + η·f_t, 0.3, 0.7)`，`λ_self = 1 − λ_exp`。

**门控**：**沿用基础 evolver 自己的验证集接受准则**，VCE 不另设阈值；它只把"验证有没有变好"记成 `f^V` 用来调权重。所以它是这一族里少见的"**不改门控、只改提案来源**"的工作。

**关键参数**：约 **20 轮**迭代；`K=5`（降到 4 只差 0.02–0.11 分，升到 7 反而掉 1.11–1.88 分）；`η=0.1`（调到 0.2 会掉 2.28–3.88 分）；`λ` 初值各 0.5，裁剪区间 `[0.3, 0.7]`。成本：蒸馏约 0.5M + 演化约 0.6M ≈ **1.1M tokens**（相对基础 evolver 约 +10%）。

**一个值得抄的设计**：裁剪到 `[0.3, 0.7]` 的含义是**任何一方都不能被永久忽略**——否则一旦某轮运气好全押外部经验，之后就再也不会去看轨迹证据了。

前后对比（Qwen3.5-27B，5 个基准平均）：

| 配置 | 平均分 | 相对基础 evolver |
|---|---|---|
| 无技能 | 47.35 | — |
| LLM 技能 | 48.01 | — |
| EvoSkill | 51.31 | — |
| **EvoSkill + VCE** | **55.44** | **+4.13** |
| SkillClaw | 53.65 | — |
| **SkillClaw + VCE** | **57.39** | **+3.74** |
| SkillOpt | 56.80 | — |
| **SkillOpt + VCE** | **60.27** | **+3.47** |

摘要口径：平均分 **+3.20 ~ +4.98**，且跨模型迁移更好。

**③ 场景与数据集**
5 个基准：SearchQA、OfficeQA、ALFWorld、Spreadsheet、BFCL-v4；4 个 LLM；**3 个基础 evolver**（EvoSkill、SkillClaw、SkillOpt）+ 2 个非进化基线。动机研究的数据：从 GitHub 与 ClawHub 采集相邻版本变更，与轨迹变更做配对，每源 400 个"技能变更单元"，用 LLM judge 按统一分类学打标（人工抽检 100% 通过）。关键发现：轨迹驱动的改动高度集中在 instructions（BFCL 372/400、SearchQA 379/400），而公共历史覆盖更广，并带来轨迹里没有的意图/模式类别。

## 4. EvoSkill v2：把"进化器"做成有状态的 coding agent

*Huang, Nama, Alzubi，2026-10，[arXiv:2610.25931](https://arxiv.org/abs/2610.25931)*

**① 优化什么**
agent 被给定的 **instructions（skills）**，**模型与执行框架（harness）都保持不变**。三个 agent 分工：benchmark adaptor（把"基准 + grader"变成插件）、solver（做题）、evolver（读 rollout 改写技能）。

**② 怎么优化**

> 一句话：把优化对象**严格锁死在 skill 文件夹**——模型、harness、grader 全都不许动；一个贯穿全程、带 bash 的 stateful agent 读训练轨迹，直接把下一版技能写进 staging。

**每轮流程（5 步）**

1. **基准适配（BA，Claude Code + Sonnet 5.5）**。用户只给三样：benchmark 的自然语言说明（数据在哪、用哪个 split、solver 拿到什么/要产出什么、跑多少）、数据集、以及一个 grader 函数 `grade(task, snapshot)`（读 attempt 结束时 solver 的工作目录，返回 0–1）。BA 产出两件：① **冻结的 plug-in**（Python 模块，列出全部 task 及其 train/validation/test 归属，以及 grader 要读的字段）；② **reference folder**（除 val/test 材料与 grader 之外的全部内容）。**split 在写第一个 skill 之前就固定**，且 BA 必须把 grader 与 held-out 信息排除在 reference 之外（作者逐项人工核查）。
2. **Solver 执行**。输入首条 user message + 当前技能集。技能通过**渐进式披露**生效：上下文里常驻每个技能的**名字和一行描述**，**body 只在描述匹配任务时由 tool call 载入**。每个 epoch 对每个 train、val 任务各试 **3 次**。
3. **打分**。用**用户提供的 grader**，不是 agent。SpreadsheetBench 先在 LibreOffice 重算全部公式、再逐 cell 对比参考簿；τ³ 比对最终数据库状态或 action 调用。**全或无**：所有检查都过才得 1。
4. **Evolver 改写**（**整轮 run 只有一个 stateful session**）。输入 `/evo/traces/epoch_K`（训练 attempt 的 session log）、`/evo/scores/epoch_K.json`（0–1 或 `grader_failed`）、`/evo/solver_workspaces/epoch_K`、`/evo/skills/epoch_K`、`/evo/reference`；输出写进 `/evo/staging`（下一版技能，**起点是它自己上次留下的**）和 `/evo/evolver_workspace`（私有笔记）。**每轮技能一律接受，没有 keep-if-better**。
5. **收尾评测**。末轮技能在 **held-out** 上每任务独立跑 3 次。

**三个刻意的"不"**

- **evolver 只见训练材料**：val/test 的 attempt 与分数由 orchestration layer 屏蔽、永不上传。否则"分数变好"可以靠改 split、改可见材料，而不是靠更好的技能。
- **不接受/淘汰式筛选**：在带噪分数上做 keep-if-better，会否掉真实的好改动。
- **grader 必须由用户提供**：v1 曾经找到并利用 SpreadsheetBench grader 的缺陷（只比对公式旁的缓存值、不重算），所以这里 grader 全程不可被 evolver 触碰。

**关键参数**：每 task 每 epoch **3 次**尝试，epoch 0 无技能；SpreadsheetBench 每次 attempt **20 分钟墙钟 + 45 turn**、11 GiB 内存、禁用 web search/fetch/子 agent、只可访问模型 API；split **57 train / 57 val / 104 held-out**（297 题按三类过滤到 218）；τ³ 为 19/20/31；held-out episode 数 104×3=312、31×3=93。**总 epoch 数未找到**。

**优化前后对比**（SpreadsheetBench v2 细粒度真值，312 个 episode）

| 条件 | 通过数 | 相对更强 baseline | epoch 成本 | 每提升一个点的成本 |
|---|---|---|---|---|
| no skill | 81/312 | — | — | — |
| SkillBoost | 101 | — | $13.95 | $2.18 |
| SkillOpt | 102 | — | $8.56 | $1.27 |
| **EvoSkill v2** | **126** | **+7.7pp** | $12.84 | **$0.89** |

其余结果：

- **τ³-bench banking（细粒度）**：48/93，baseline 最多 43（**+5.4pp**）。
- **只有 pass/fail 的稀疏反馈**：no skill 81 / SkillBoost 85 / SkillOpt 107 / EvoSkill v2 105 —— **与 SkillOpt 持平，但成本不到其十分之一**（per point $0.07）。
- **弱模型也能自改进**：Haiku 5.5 同时当 solver 与 evolver，held-out 通过率最多 **+21.5pp**。
- **失败高度可重复**：SpreadsheetBench 上"至少失败过一次"的任务里约**九成**是三次全败，τ³ 上约六成——这既解释了新手任务为何要多次尝试，也说明**重试救不了多少**。

**③ 场景与数据集**
SpreadsheetBench v2 与 τ³-bench（banking 域）；两种反馈设置（有细粒度真值 / 无）；因为是"用户提供基准 + grader、由 adaptor 生成插件"，方法本身是**基准无关**的。

## 5. SkillReducer：唯一明确把 `description` 当主目标的工作

*Gao et al.（港科大等），2026-03，[arXiv:2603.29919](https://arxiv.org/abs/2603.29919)*

**① 优化什么**
把技能当成**可分层的软件工件**，形式化是 `s = (d, b, R)`：`d` = 路由描述（description）、`b` = 主体（SKILL.md 正文）、`R` = 可选的引用文件集合（**scripts 不在优化范围内**）。目标是

> 在"路由等价 + 功能保留"两个约束下，最小化 `Cost(s) = |d| + |b| + Σ_{r∈R} |r|`

产出的新技能 `s'` 由三部分构成：**1-minimal 的描述**（每个子句都是必要的）+ **总是加载的核心模块 `b*`** + **只有 agent 显式 `read_file` 时才加载的按需模块 `R*`**。

所以它同时动你说的三样东西：`description`（压到最小、或从无到有地生成）、正文（按"必须常驻 / 按需加载"重新分层）、以及引用文件（跨文件去重后转为按需模块）。

**② 怎么优化**

> 一句话：先用**用户查询驱动的 delta debugging** 把描述压到 1-minimal，再用**五类内容分类**把正文切成"总是加载的核心规则"与"按需加载的示例/模板/背景"，最后用**忠实性 + 任务表现两重质量门**兜底。

**先做诊断（决定了后面两步怎么设计）**：对 **55,315 个公开技能**做实证，并标注了 15,107 个段落，得到三个系统性问题——**26.4% 的技能完全没有 routing description**、**>60% 的正文本内容不可执行**、reference 文件每次调用可注入数万 token。

**Stage 1：压路由描述（目标：压到 1-minimal，但不许丢触发能力）**

1. **切分**：LLM 把 `d` 切成"语义子句"集合 `U`。选子句而不是句子，是因为句子级太粗（一句里混着必要与非必要）、词级太细（拆完语义不成立）。
2. **造裁判**：候选池 `C` = 目标技能 + **4 个 TF-IDF 最相似的干扰技能** + **1 个 LLM 生成的"影子"对抗技能**（同领域但用途不同）；每条 query 的候选顺序随机打乱，防位置偏置。
3. **定义 oracle**：`O_sim(d, Q, C) ∈ {0,1}`——**只有所有 query 都选中了目标技能才判 1**。也就是"压完之后，它在相似干扰项里仍然能被正确路由"。
4. **ddmin 二分删除**：用 `O_sim` 递归二分地删子句，直到删掉任何剩余子句都会让 oracle 判 0，得到 **1-minimal** 子集。代价是 `O(n log n)` 次 oracle 调用，而不是穷举的 `O(2^n)`；单次调用约 2 秒。
5. **逐单元改述**：对保留下来的每个子句试更短的写法，`O_sim` 通过才接受；最后做一次整体 Polish 拼接。
6. **真实环境验证（Phase 2，防止"模拟 oracle 过于乐观"）**：把压缩后的描述装进真实技能目录，用 Claude Code CLI 真的发 query、解析 stream event 判断有没有触发。判定标准是**"原描述能触发的 query 集"必须全部仍然触发**；不满足就**贪心加回**最能提升触发率的被删单元（最多 3 步），仍失败则整体回退原描述。
7. **补描述分支**：对缺失或过短（≤40 token）的描述，从正文抽三类路由信号——主要能力、触发条件、唯一标识符，每条 20–40 token；先过 Phase 1 的 oracle，再在抽样子集上做 Phase 2 验证。

**Stage 2：重构主体（目标：把"常驻"与"按需"分开）**

8. **分段分类**：给每个段落打一个标签，五选一 `{core_rule, background, example, template, redundant}`。
9. **类型特化处理**：`core_rule` → 压成核心模块 `b*`（永远加载）；`example` / `template` → **每概念只留一条最好的**（去重）；`background` → 摘要成按需模块，**并给模块写"何时该读"的元数据**（否则模型不知道该去读它）。
10. **跨文件去重**：对每个引用文件做 `RemoveOverlap(r, b)`，剩余 **≥30 token** 才保留并压成按需模块（太短就并入正文）。
11. **两重质量门**：
    - **忠实性检查**：LLM 判官核对每个关键操作概念是否仍存在于"核心或按需模块"里，缺失则**回滚该部分**；
    - **任务评估**：每个技能生成 5 个任务，在"无技能 / 原技能 / 压缩技能"三条件下跑，`retention = min(score_压缩 / score_原技能, 1)`；若压缩后低于原技能，**反馈回路把缺失信息提回核心模块**。

**关键参数**

| 参数 | 含义 | 论文取值 |
|---|---|---|
| 压缩器 / 判官 | 执行模型 | DeepSeek-V3，温度 0，结构化输出 |
| 判 1-minimal 的依据 | 干扰项配置 | 4 个 TF-IDF 干扰 + 1 个影子对抗 |
| 补描述阈值 | 多短算"缺失" | ≤40 token；单信号 20–40 token |
| 回补步数 | 真实环境恢复上限 | ≤3 步 |
| 模块保留阈值 | 去重后多短就丢弃 | 30 token |
| 质量门样本 | 每技能生成任务数 | 5 个 |
| tokenizer | 计数口径 | cl100k_base |

**为什么这么设计**：作者明确说模拟 oracle "may be overly optimistic"，所以做成两阶段——**快筛（模拟）+ 真实触发验证 + 选择性回补**，而不是一次压到底。也不用 LLMLingua 式的 token 剪枝：技能把规则、示例、背景混在同一份文档里，单纯删 token 会同时破坏"路由正确性"和"任务表现"，而 **"compression must preserve both routing correctness and task performance"**。

**优化前后对比**

| 指标 | 结果 |
|---|---|
| 描述压缩 | **−48%** |
| 主体压缩 | **−39%** |
| 功能质量 | **+2.8%**（p=0.002, d=0.107）——删掉非必要内容反而更好 |
| 任务评估通过率 | 86.0% |
| SkillsBench | **100% 通过**，主体 token 最多 **−75%** |
| 路由保持 | 600 个技能经选择性恢复后 **100%** |
| 跨模型保留率 | 5 个模型 / 4 个家族平均 **0.965** |
| 单次调用成本 | 约省 1,000 token |

对照组是同 token 预算下的 **LLMLingua / 直接 LLM 压缩 / 截断 / 随机删除**。

> 可靠性说明：本篇的超参与部分阶段细节在原文抓取时被截断，上面的数字已与摘要核对一致，但少数参数（如判官模型、阈值）来自二次来源（alphaXiv 概述），引用前建议回原文核一遍。

**③ 场景与数据集**
实证语料 **55,315 个公开技能**；评估用 **600 个技能 + SkillsBench**；跨 5 个模型（4 个家族）。

> 对你的问题直接的回答：**name/description 确实是被单独优化的一层，而且现状很差（四分之一以上没有 description）。** 如果想改进自己的技能包，优先级应该是：先把 description 写对（路由），再瘦身正文。

## 6. MetaSkill-Evolve：把"怎么改进"也变成可进化的对象

*Wang et al.（慕尼黑大学等），2026-07，[arXiv:2607.05297](https://arxiv.org/abs/2607.05297)*

**① 优化什么**
每个进化分支同时携带 **task skill `s`**（做什么）和 **branch-local meta-skill `m = (ψ, σ, α, π, ε)`**（怎么做改进）。这五个分量分别参数化改进流水线里的 **Analyzer / Retriever / Allocator / Proposer / Evolver** 五个 agent。也就是说，被优化的对象从"技能文件"上升到了"**改进技能的那套流程**"。

**② 怎么优化**

> 一句话：把"怎么改进"写成一份和任务技能**同格式的 Markdown**，于是同一条流水线既能改任务技能（快循环），也能改这份"改进规程"（慢循环）——不需要额外模型，也不需要额外框架。

**A. 快循环：每个候选技能走一遍（6 步）**

0. **选父（谁当前最有希望）。** archive 只收 `ΔU > 0` 的子代；父节点按 `η₁·U_v + η₂·P̂_v + η₃·N_v` 取最大，其中 `U` 是当前效用，`P̂` 是**元生产力**（它所有子节点 ΔU 的均值，没有子节点记 0），`N = 1/(1+被选中次数)` 是冷却项。效果是"钱投给还在产出好后代的分支"，同时给冷门分支留机会。选中后把 `(s_v, m_v)` 从数据库恢复到磁盘，各 lineage 相互隔离。
1. **Analyzer(ψ)**：读父技能在训练 batch 上的**最差样本**及其轨迹，输出根因 `a`、失败标签 `φ`（≤15 词）与"该改哪个技能"。若解析 final_answer 失败，就逐 step 扫描；仍失败则再发一次带 constrained response_format 的修复调用。
2. **Retriever(σ)**：拿 `φ` 去检索"灵感"——先按 tag 相似度 **over-fetch 3 倍**（同分支 + 跨分支），再由 LLM 重排，输出 inspirations `I`。
3. **Allocator(α)**：定这一轮给多少条子预算 `K ∈ [1, K_max]`。**停滞时放大 K**（多试几种改法）。
4. **Proposer(π)**：输入（最差样本 `f`、根因 `a`、灵感 `I`），输出编辑 `δ`（改哪一节、改什么、为什么改）；`K>1` 时附加 diversity hint，让多个候选彼此不同。
5. **Evolver(ε)**：把 `δ` 真正落到磁盘，写回后做 before/after **hash 比对**确认落盘（hash 没变即视为失败），并刷新技能注册表。
6. **评分入档**：每个子代在验证集上算 `ΔU`，`>0` 入 archive；`≤0` 不入档，但**仍留在图里供 σ 检索**——负结果也是资产。

**B. 慢循环：每 H 轮，改"改进规程"本身（1 步，但有三处专门设计）**

7. 把最近 `H` 个后代的失败标签、诊断与 `ΔU` 汇成一条**合成元失败轨迹** `f_m`，然后用**同一条流水线**去改写 `ψ…ε` 这五个文件。三处关键设计：
   - **受限 Analyzer**：target 必须属于 `{ψ,σ,α,π,ε}`，否则退化为 round-robin 轮换——防止它跑去改任务技能；
   - **整体重写**：五个文件一起改，保证彼此一致（而不是各改各的）；
   - **串行叠加**：`K_m` 个改动依次作用，而不是并行覆盖。

**关键参数**

| 参数 | 含义 | 论文取值 |
|---|---|---|
| `η₁, η₂, η₃` | 效用 / 元生产力 / 冷却的权重 | 1.0 / 0.5 / 0.25 |
| `H` | 慢循环周期（几轮合并一次） | 2（扫描 2/4/8） |
| `K_max`（初始 K） | 每轮子预算 | 3（初始 2） |
| frontier | 前沿大小 | 3 |
| 跨分支检索概率 | 从别的 lineage 借灵感的概率 | 0.2 |
| 灵感条数 | 同分支 / 跨分支 | ≤3 / ≤2 |
| over-fetch | 检索先放大倍数 | ×3 |
| 训练 batch | 每次分析多少样本 | 6 类 × 3 样本 |
| 早停 | 连续多少轮无提升 | 5 |
| backbone | 五个 agent 共享 | 同一**冻结**模型（二次来源记为 Gemma-4 31B，未从原文核实） |

**为什么这么设计**：作者对既有系统的判断是——它们 "improves only the task skill (what the agent does) while the improvement procedure … is authored once and held fixed"（只改任务技能，改进规程写一次就固定）。所以这里把规程也降级成同格式技能，于是 "no extra model and no extra framework"。两个刻意收敛的选择：递归**只做一层**（不产生 meta-meta-skill）；多样性"**是打分的性质，不是结构上的约束**"（不做 lineage 预筛，让分数自己把好的挑出来）。

**优化前后对比**（held-out test accuracy，逐级叠加）

| 基准 | No-Skill | Static Skill | 单层进化 | **MetaSkill-Evolve** | 相对裸 backbone |
|---|---|---|---|---|---|
| OfficeQA | 31.78 | 36.09 | 48.94 | **55.32** | **+23.54** |
| SealQA | 29.17 | 29.41 | 37.21 | **45.26** | **+16.09** |
| ALFWorld | 92.31 | 90.38 | 92.31 | **94.23** | **+1.92** |

读法有两个要点：
- **相对"单层进化"才是这篇的真正增益**：OfficeQA +6.38、SealQA +8.05，而 ALFWorld 只有 +1.92（且 static skill 反而掉 1.93）——元层进化的收益强依赖任务类型，知识密集型吃得多，具身决策几乎吃不到。
- **消融显示最承重的是 Allocator(α)**：去掉它 OfficeQA 掉到 35.58（−19.74，最大单项损失）；去掉 Proposer(π) 则 SealQA 36.84（−8.42）、ALFWorld 86.54。
- **慢循环不是越勤越好**：`H` 扫描在 OfficeQA 上是 48.94 / 41.35 / 39.84（对应 H=2/4/8），**更频繁的元层更新反而更差**。

**③ 场景与数据集**
OfficeQA（文档问答）、SealQA（检索问答）、ALFWorld（具身决策）。

> 这篇是整条线里唯一真正"递归"的工作：其他工作优化 `s`，它优化 `s` **和** 产生 `s` 的 `m`。

## 7. SkillOS：训练一个"策展人"，技能库自己长结构

*Ouyang et al.（Google Cloud AI Research / UIUC / MIT），2026-05，[arXiv:2605.06614](https://arxiv.org/abs/2605.06614)*

**① 优化什么**
**技能库（SkillRepo）里的技能文件**。每个技能是单个 Markdown 文件，两个部分：(i) YAML frontmatter（**技能名 + "何时该用"的描述**），(ii) Markdown 指令（可执行知识、工作流、约束、可复用启发式）。策展人通过**函数调用**做 `insert_skill` / `update_skill` / `delete_skill`。→ 元数据与正文都会被写，但**被训练的是"策展策略"本身**。

**② 怎么优化**

> 一句话：不手写"什么时候加技能、什么时候改技能"的规则，而是**把一个策展模型用 RL 训出来**，让它自己学会 `insert / update / delete`。

**一个训练 step（5 步）**

1. **采一组相关任务** `G`（先用 Gemini-2.5-Pro 给任务打"潜在属性"标签，再按依赖与相似度分组），并把 SkillRepo **清空**：`S_0 = ∅`。→ 从零开始，逼 curator 学会"从无到有地积累"。
2. **组内逐任务执行**：BM25 从库里检索 top-k → 冻结 executor 执行 → 轨迹 `ξ_i`；再用 LLM-as-a-judge 给一个 0/1 正确性。
3. **策展**：可训练 curator 以（轨迹、正确性、本轮检索到的技能）为输入，输出操作序列；动作只有三种函数调用——`insert_skill` / `update_skill` / `delete_skill`，由 `ApplyOps` 落到库里。
4. **算复合奖励**：`r = r_task + λ_f·r_fc + λ_u·r_cnt + λ_c·r_comp`。四项分别是：`r_task` = 组内**第 2 个任务起**的平均成功率（第一个任务只用来"喂经验"，不计分）；`r_fc` = 有效函数调用占比；`r_cnt` = 外部 judge（Qwen3-32B，**与 executor 不同源**）打分；`r_comp = 1 − |S_i|/|χ_i|` 惩罚库膨胀。
5. **GRPO 更新 curator**：每组采 8 条完整策展序列，优势 `A^n = r^n − 组均值`，按 clip 的代理目标更新，优势**均分到整条序列的所有 token** 上。

**两个必须点明的性质**——它和前面几篇的关键差别：

- **没有验证门控。** curator 直接改库，全靠 RL 奖励 + on-policy 采样来约束。这与 SkillOpt / SkillBoost 那种"留出集不涨就不接受"是**完全不同的哲学**：一个靠门，一个靠罚。
- **它真的会改权重。** 训练的是 curator（Qwen3-8B），executor 冻结但同源。所以它在这条线里属于"**改权重 + 改文本**"的混合体，而不是纯文本优化。

**关键参数**：lr 1e-6、batch 32、GRPO group 8、温度 1.0、steps 60/50/100（ALFWorld / WebShop / reasoning）、max prompt 16,384 / response 4,096、检索 top-k=5、max turns 30/30/1、action history 3、组大小 10/10/Random(5,12)、`λ_f=1.0`、`λ_u=0.1`、`λ_c=0.05`。

**为什么奖励要这样拆**：单给任务成功率，curator 学不到"操作合不合法""技能写得对不对""库是不是臃肿"这些中间信号；而 `r_task` 只从组内第 2 个任务起算，是为了保证**前面的经验真的被后面用上了**才给分。

前后对比：相对最强 baseline **最高 +9.8% 相对提升**，交互步数 **−6.0%**；**8B 的 curator 直接当 curator 用也胜过 Gemini-2.5-Pro**；跨 executor backbone 与跨任务域都能泛化。定性发现最有趣：**技能逐步演化成结构更丰富的 Markdown，编码出更高层的 meta-skill**。

**③ 场景与数据集**
多轮 agentic 任务（含 WebShop，指标：成功率 / WebShop Score / 交互步数）+ 单轮推理任务（准确率）；对比 memory-free 与强 memory-based 基线。

## 8. Selm：把技能库当作数据库来管（CRUD + 生命周期）

*Hu et al.（中国人民大学 / 北京智源），2026-10，[arXiv:2610.24630](https://arxiv.org/abs/2610.24630)*

**① 优化什么**
**整个库**。技能形式化为五元组 `sₖ = (n, d, c, t, γ)`——**name、description、instruction content（正文）、trigger conditions、task category**，外加两个状态量：**confidence**（被更新操作支持的程度）与 **utility**（历史上好不好用）。操作集把数据库的 CRUD 搬过来：`ADD / EDIT / UPVOTE / DOWNVOTE / DELETE`。

**② 怎么优化**

> 一句话：把技能库当**持续运营的资产**管——检索看"相关 + 历史上好不好用"，更新按类别 Map-Reduce 只改相关技能，留存退役由两路信号决定。

**每轮 10 步**

1. **检索**：先按任务类别 `γ_i` 过滤（保留同类或标为 "general" 的技能），再按 `R(s,x_i) = (1−w_u)·R_rel(s,x_i) + w_u·u(s)` 排序取 top-k 注入。→ **相关性回答"像不像"，utility 回答"好不好用"**，线性加权。
2. **Rollout**：冻结模型 + harness 执行，拿回轨迹 `τ_i` 与两个分数——`r_hard ∈ {0,1}`、`r_soft ∈ [0,1]`（多项检查时 `r_soft = n_pass/n_total`、全过才 `r_hard=1`；参考答案比对时 `r_soft` 是 token 级重叠、`r_hard` 是精确匹配）。
3. **奖励合成**：`r_i = G(r_hard, r_soft)`——hard 指标取 `r_hard`，soft 取 `r_soft`，mixed 取 `(1−w)·r_hard + w·r_soft`。
4. **效用回写**：`u(s) ← (1−α)·u(s) + α·r̄_s`（EMA，`r̄_s` = "检索到该技能的那些任务"的平均奖励）。→ 下一轮检索直接吃到新 utility。
5. **挑最该看的轨迹**：`ū` 是该任务所检索技能的 utility 均值，优先级 `p_i = |r_i − ū|`，取最大者。→ **差距大 = 库的信念被这次执行反驳了**，这才是最值得分析的证据。
6. **Map（按类别分析）**：轨迹按任务类别分组，`TrajectoryAnalyst` 逐类总结成功模式、失败模式与新洞见。→ 防不同类别的经验互相覆盖。
7. **Reduce（合成操作）**：`SkillSynthesizer` 结合技能内容、confidence、utility 与类别反馈，产出**有界**的 CRUD 操作集 `{ADD, EDIT, UPVOTE, DOWNVOTE, DELETE}`。
8. **落盘**：已有技能上调 `v(s) ← v(s) ± 1`（UPVOTE / DOWNVOTE 改 confidence）。
9. **验证门**：更新后的库在 `D_sel` 上评估，**通过才保留**。
10. **生命周期**：低 utility 技能退役进 **graveyard**；**graveyard 阻止同名技能再次入库**——防止"删了又长回来"的振荡。

**为什么 confidence 和 utility 要分开**：**confidence** 记录"被更新操作支持的程度"（投票 ±1），用于**留存决策**；**utility** 记录"历史上好不好用"（奖励 EMA），用于**检索排序**。分开的好处是：一个"本轮没用、但以后可能有用"的技能，utility 暂时低而 confidence 没掉，就不会被误删。这一条是它和"每轮局部编辑"最本质的差别。

**参数**：符号层有 `w_u`（utility 权重）、`α`（EMA 系数）、`k`（top-k）、`w`（mixed 奖励权重）；**具体数值未找到**（附录 C 超参表在抓取截断之后）；confidence 初值、utility 初值、graveyard 触发门限、**验证门的比较规则**同样**未找到**。

**优化前后对比**：论文只报"在多数设置上最优（state-of-the-art among skill-evolution methods）"，**逐项数值未取到**（§5.2 在截断之后）。baseline 是单文档优化（SkillOpt / SkillGrad 一类）与先前的多技能系统。

**③ 场景与数据集**
四个 agent 基准，覆盖不同任务领域与执行环境（基准清单见其附录 B）。演进分析单独一节（库如何增长/退役）。

## 9. Library Drift：技能库会"漂移"，而且是静默的

*Zhang et al.（Amazon Science），2026-05，ICML 2026 FAGEN workshop，[arXiv:2605.19576](https://arxiv.org/abs/2605.19576)*

**① 优化什么**
**不是单份文档，而是库的生命周期治理策略**：① 按实测贡献淘汰技能；② 活跃库**宽度上限 C**；③ 元技能写作先验（约束合成）。同时提出一套**可观测性三件套**：append-only 证据日志、每个技能的贡献分、router 命中率。

**② 怎么优化**

> 一句话：**先证明漂移真实存在，再只用三样东西修它**——按测量贡献退役、库宽度硬上限、meta-skill 写作先验；所有判断都来自一份**只追加的证据日志**。

**系统骨架：五个角色 + 一份日志**（同一个冻结模型 Claude Opus 4.7 扮演，靠角色 prompt 区分）

| 角色 | 做什么 | 关键约束 |
|---|---|---|
| **Router** | 两阶段检索：tf-idf 与 embedding 各取 top-10 合成候选，再由 LLM 决定"注入哪一个 / 都不注入（NONE）" | 库 ≤20 个 active 时直接看全库二选一 |
| **Solver** | 执行任务 | **单次调用，无工具、无执行反馈、无自我修正**（刻意做弱，让增益只能来自技能库） |
| **Grader → Capsule** | 跑测试，把每条 `任务 × 技能 × 尝试` 的成败写成一条 capsule | 只追加，不改写 |
| **Critic** | 对**每一条训练失败**单独发一次调用，输入任务、注入的技能、Solver 输出、grader trace；输出 `{helped/hurt/neutral/inapplicable}` + pattern + confidence | 这是最贵的一步 |
| **Synthesizer** | 按 canonical pattern 聚类 verdict；**同一 pattern 至少 3 条失败**才允许合成新技能；"已被覆盖"守卫（余弦 ≥ 阈值就跳过） | 产出 YAML 要过校验、去重、长度上限 |
| **Curator** | **不含 LLM，纯算术**：`ĉ(s) = (successes − failures) / trials` | 只改 status，不删证据 |

**治理就三件事**
1. **按测量贡献退役**：`n(s) ≥ Nmin` 且 `ĉ(s) ≤ −τ` 才退役。取 `Nmin=100`、`τ=0.10`，对应 Hoeffding `ε ≈ 0.20`——**先攒够证据再动手**。
2. **库宽度硬上限** `C = 50`：合成会超上限时，淘汰 `ĉ` 最低的那个。
3. **meta-skill 写作先验**：用一份 meta-skill 约束新技能的写法。

**三个"痕量信号"是这套方法的另一半**：`ĉ(s)`（每个技能的净贡献）、**hurt 比例**（Critic 判 hurt 的占比）、**Router engagement**（注入率）。失败会在总分掉下来之前，先在这三个信号上露头——这就是"把沉默失效变可见"的具体做法。

**八个单旋钮消融**（MBPP+ hard-100，100 轮，3 seeds）

| 条件 | rolling gain | 说明 |
|---|---|---|
| **Default（完整配方）** | **+0.328 ± 0.018** | 0.258 → 后期均值 0.584（峰值 0.658） |
| A1 不注入技能 | +0.002 ± 0.005 | engagement 0；平底，不坏也不涨 |
| A2 绕开 LLM 门控、只注入 top-1 | +0.077 ± 0.065 | engagement 98% 但质量差——**"能说 NONE"本身就是防漂机制** |
| A3 去掉 meta-skill | +0.187 ± 0.036 | 少 +0.141，先验是最承重的组件之一 |
| A4 证据不足就退役（Nmin 100→20、τ→0） | **−0.019 ± 0.010** | 库塌到 **2 个 active**，pass@1 反而低于无技能基线 |
| A5 关闭 pattern 去重 | +0.374 ± 0.023 | 略好于 Default——显式去重误杀多于其挡下的重复 |
| A6 显式去重 | +0.363 ± 0.033 | 同上，结论一致 |
| A7 库宽上限加倍（C=50→100） | +0.317 ± 0.110 | 方差变大，变差 |
| A8 每 10 轮重写 meta-skill | +0.372 ± 0.017 | 增益边际，但墙钟 10.1h vs 6.5h |

这张表最值得记的两条：**A4 的负收益**（证据不够就淘汰 = 主动破坏）与 **A2 的低分**（没有"拒绝注入"这扇门，检索反而拖累）。

**实验是怎么搭的（这点很关键）**：MBPP+ test 共 378 题，**先剔除 Claude Opus 4.7 在 5 个基线 seed 上全对的约 273 题**，剩下随机取 **100 题**（60 train / 40 eval，固定 seed）。也就是**刻意只用"模型本来就做不对"的题**，否则天花板效应会把增益压没。baseline = 各条件第 0 轮的 pass@1（那时还没任何技能），增益定义为"末 10 轮均值 − 首 10 轮均值"。

**成本**：Default 跑 100 轮约 **1.45 万次 LLM 调用**（1 万 solver + 4.3 千 critic + 152 次合成），比 A1 多 43%，墙钟 6.5h vs 2.3h。Critic 占了近三分之一——**"给每条失败单独做归因"是这套方法真正的开销所在**。

**引用的外部对照**：SkillsBench 上 **LLM 自写技能 +0.0pp vs 人工策划 +16.2pp**（对应 SkillsBench 摘要的 +16.6pp，口径略有差异）。

**③ 场景与数据集**
MBPP+ hard-100（100 轮连续进化）；引用 SkillsBench 作外部对照。

## 10. Ratchet：退役一个技能，judge 得多准？

*Zhang et al.（同团队，同一代码库），2026-05，[arXiv:2605.22148](https://arxiv.org/abs/2605.22148)*

**① 优化什么**
**淘汰规则本身**。场景极简：管理技能库时你每个技能只有一个**带噪标量**（分数），要据此决定"留还是退"。

**② 怎么优化**

> 一句话：它不教你怎么改技能，而是**先证明"用总分管库"在什么条件下必然失效**，再给一个带下界保证的治理配方。

**每轮六个阶段**（同一个冻结模型扮演五个角色，Curator 只做算术）
1. **Eval pass**：Router 只在 active 技能上路由，产出用于汇报的 held-out capsule。
2. **Train pass**：同一条管线跑训练划分，失败即合成原料（bootstrap 期连候选技能也参与路由，好攒初始证据）。
3. **Critic**：每条训练失败发一次调用 → `{helped/hurt/neutral/inapplicable}` + pattern + confidence。
4. **Synthesizer**：读最近 `W=6` 轮 verdict；pattern 归一化用两两余弦 + union-find（`τ_canon=0.85`）；聚类后**簇 ≥3** 才成为合成目标；"已被覆盖"守卫（余弦 ≥0.85 跳过）。
5. **Curator**：`ĉ(s)=(pass−fail)/n`；`n(s) ≥ Nmin` 且 `ĉ(s) ≤ −τ` → 退役（**只改 status，不删证据，可再启用**）；超上限 `C` 时淘汰 `ĉ` 最低者。
6. **回滚门**：某轮 held-out pass@1 比历史最佳低超过 `τ_rb=0.10` 记一次 regression，**连续 5 次**才回滚到最佳快照（单轮噪声不触发），回滚后要归档审计。

**Prop.1：治理过的技能架有个"地板"**
在三个条件下——(i) Router 检索一致（对任务 x 只会选 NONE 或某个 `s`），(ii) `ĉ` 是 `c` 的无偏一致估计，(iii) `Nmin` 保证以 ≥1−δ 的概率所有 active 技能满足 `|ĉ − c| ≤ ε`（Hoeffding）——有

> `E[pass@1] ≥ E[p0] − (τ + ε) − Cδ`

思路很直观：对 `|S_t| ≤ C` 做 union bound，则大概率所有存活技能 `c(s) ≥ ĉ − ε ≥ −τ − ε`；路由到技能的任务至少还有 `p0(x) − τ − ε`，路由到 NONE 的就是 `p0(x)`，对数据分布取期望即得。**C 与 τ 缺一，这个界就失去内容**——无界库没有有限类比。这就是"为什么要设库宽上限"的定量理由。

**judge 结论：标题那句话的确切含义**
把 judge 建模成二值信道，两个错误率：`ρ_{F→P}`（失败判成通过）、`ρ_{P→F}`（通过判成失败）。**τ 的定义是退役边际**：`ĉ(s) ≤ −τ` 即退役；由于 `ĉ = (pass − fail)/n`，这等价于门槛通过率 `π_τ ≡ (1−τ)/2`。于是：

> **当 `ρ_{F→P} ≥ π_τ = (1−τ)/2` 时，任何样本量 `n` 都退不掉任何技能**——不是"难退"，而是**恒不退**。

机制：假通过会把 `ĉ` 的均值**单向推高**，而且偏移恰好落在最该退役的那些技能上；**这个偏差不随 n 消失**，所以"多采样"救不了均值位移。对称的另一侧：越过 `ρ_{P→F} = 1 − π_τ` 就会**一律被退役**（starvation）。两条边界都平行于坐标轴，所以**可治理区是一个矩形**，角点在 `(π_τ, 1−π_τ)`。由此有个反直觉推论：**最危险的不是"全瞎"的 judge，而是"半瞎"的**——伤害在边界处最大。

实测审计里，这个 judge 以约 **45 倍余量**通过"假通过悬崖"，但落在 starvation 边缘之外——方向安全，只是损失分辨率。

**一个负面结论值得单列**：**终局任务分数是个坏警报器**——它最多只移动受治理增益的约 **1/5**，且对 `ρ` **非单调**。所以监控库不能用总分，只能看 `ĉ`、hurt 比例、engagement。

**关键参数**：`τ=0.10`、`Nmin=100`、`C=50`；`δ=1e−3/skill → ε≈0.20`、`Cδ=0.05`，故下界为 `E[p0] − 0.35`；`W=6`、`τ_canon=0.85`、簇 ≥3；Router 两阶段 top-10（tf-idf ∪ embedding）+ LLM 门；`τ_rb=0.10` 且需连续 5 次。

**实验**：MBPP+ hard-100（378 题里剔除全对的、取 100：60 train / 40 eval），100 轮、3 seeds（42/7/13），报 mean±std；另有 7 模型跨模型探针 + 换 solver，并迁移到 **SWE-bench Verified 跑 20 轮（峰值 +0.22）**。Solver 同样是单次调用、无工具无自省——让增益只能来自库。

**③ 场景与数据集**
MBPP+ 的 hard 切片；**无参考（reference-free）设置**下由 LLM judge 打分——正因如此标量才有噪声。

## 11. Repo2Skill-Evo：技能会对着代码库"静默过期"

*Duan et al.，2026-08，[arXiv:2608.21964](https://arxiv.org/abs/2608.21964)*

**① 优化什么**
**过期技能的维护**：给定一个 V1 技能集和官方的 V1→V2 patch，agent 要**更新已过时的内容、保留仍然有效的指引**。目标不是"让技能更强"，而是"让技能不过期"。

**② 怎么优化**

> 一句话：把"仓库技能过期"做成一个**可评测的维护任务**——给你 V1 技能集和官方 V1→V2 patch，只许改过期部分、不许动仍然有效的内容。

**任务定义**：起点是三元组 `(V1 技能集 S_V1, 官方 release patch Δ, 维护工具接口 U_maint)`；`S_V1` 由 Repo2Skill 蒸馏 + 专家修订后**冻结**，所有被评测 agent 共用。产出 `S_V2`，评的是**集合级变换** `S_V1 → S_V2` 本身。

**V1 技能集怎么来的（这一步保证公平）**

1. **蒸馏 agent**（Claude-opus-4.6 与 GPT-5.4 各产一套候选，**只用 pre-release 仓库**）：在状态 `w_t = (交互历史, 分析报告, logic read-map, 材料文档, skill 包)` 上跑 think–act–observe，动作集是 `{analyze, logic, materials, draft, validate, finish}`。`analyze` 先静态分析建符号索引（符号/文件路径 → 源码位置）；`logic` 产出 routing read-map；`materials` 收集仓库证据；`draft` 写 SKILL.md（含可选脚本与 references），并**把每条断言的来源路径与符号记成外部元数据**；`finish` 只在验证通过后终止。
2. **Grounding gate**：核对 SKILL.md 与脚本引用的路径/符号能否在 V1 仓库解析；引用数达标的候选一旦**不可验证引用占比超阈值**即判失败。注意它**只保证可解析、不保证语义正确**。
3. **人类专家**在两套候选里选较强一套，对照 V1 仓库修订验证，之后**冻结为 gold label**。

**维护 agent 怎么跑**：单 agent scaffold，只有 **6 个通用工具**（shell 执行、受限文件发现与检查、字符串编辑、终止），**没有任何任务特定的定位/修复模块**；统一 SOP prompt；turn budget 在初始化时告知、全程报告剩余。输入 `S_V1 + patch`，在工作区编辑产出 `S_V2`；预算耗尽就照评部分结果。

**怎么打分（这套指标本身是贡献）**

- **gold 过期集 `G_Δ`**：自动发现候选 + 行级人工对照 patch 的直接证据核验。
- **R**：`S_V1→S_V2` diff 的**删除侧**里的 V1 行（含改写）；**新增行不计**。
- `Recall = |G_Δ∩R| / |G_Δ|`、`Precision = |G_Δ∩R| / |R|`、`F1` 由二者合成；每个 transition 跑 3 次取 avg@3 / best@3，再对 105 个 transition 做 macro 平均。
- **为什么只查删除侧**：合法的 V2 替代写法很多（语义等价），最终质量交给另一个 **NL Judge**——它从 API / Files / Info（是否保住仍有效的 guidance）/ Prompt（是否遵循 patch-grounded 指令）/ NL 五个维度各打 0–2 分，合计 0–10；结构非法的技能集直接 form-gate 为 0。

**关键设计取舍**：走 **minimal-edit 而非整体重写**——precision 项会惩罚对 `G_Δ` 之外 V1 行的改动，Info 维度专门检查"仍有效的 V1 guidance 有没有被保住"，因为一次性重生成会丢掉仓库特定知识。另外刻意用**极简 scaffold**，好把差异归因到模型行为，而不是脚手架。

**参数**：57 个公开 GitHub 仓库、**105 个官方 release transition**、共 **1,158 个 skill**；gold 集合计 **12,217 条**经 patch 核验的过期行，**每个 transition 都满足 |G_Δ| > 0**，过期行数**中位数 92**；每 transition 3 次独立 run。turn budget 数值与 grounding gate 具体阈值**未找到**。

**"优化前后"在这里是什么**：这篇**没有改造前后的对照**，主结果就是**维护成绩本身**——6 个 frontier agent 的 avg@3 macro F1 只有 **29.9%–69.7%**；每个被选 transition 的 V1 技能集都含过期内容（中位数 92 行）；两类错误互补：**覆盖不全**（技能集里没提到的文件漏改、留下陈旧内容）与**过度编辑**（recall 上去了、precision 掉下来）。在 20 个最难 transition 上给 oracle 文件级定位能提升，但**仍残留大量错误**。

**③ 场景与数据集**
57 个真实 GitHub 仓库的 105 次 release transition（配套官方 patch 作为真值）。

## 12. SkillsBench：先解决"怎么量"，再谈"怎么优化"

*Li et al.，2026-02，NeurIPS 2026，[arXiv:2602.12670](https://arxiv.org/abs/2602.12670)*

**① 优化什么**
**不优化技能**，而是给"技能到底有没有用"提供配对测量：同一套任务，在"有技能"与"无技能"两种条件下各跑一遍，用**确定性验证器**打分。

**② 怎么优化（这里其实是"怎么测量"）**

> 一句话：把"技能有没有用"变成一个**受控实验**——同一任务、同一模型、同一 harness，唯一变量是"有没有技能"。

1. **配对条件**：每个任务都跑两次，一次带人工策划技能、一次不带技能，其余完全一致。
2. **确定性验证器**：打分不靠 LLM judge，而是靠可执行检查（代码测试等），所以分数没有"judge 噪声"这一项。
3. **两种增益口径**：原始增益（百分点）与归一化增益（相对"还差多少才能全对"的比例），后者用来跨难度比较。
4. **横向扫配置**：在 18 个 model–harness 组合上重复，看增益是不是普适，而不是某个模型的特例。
5. **两个附加结论来自同批实验**：聚焦型技能（≤3 个模块）优于大而全的捆绑；小模型 + 技能可以打平不带技能的大模型。

**优化前后对比**（这里的"前"就是配对里的无技能条件）

| 指标 | 结果 |
|---|---|
| 平均通过率 | **33.9% → 50.5%（+16.6pp）** |
| 归一化增益 | **25.5%** |
| 配置级增益跨度 | **+4.1 ~ +25.7pp** |
| 技能体量 | 聚焦型（≤3 模块）优于大捆绑 |
| 模型规模替代 | 小模型 + 技能 ≈ 大模型无技能 |

**③ 场景与数据集**
87 个任务 / 8 个领域（QA、表格、文档、数学、具身等），18 个 model–harness 配置。

> 这是全线的"标尺"：Library Drift 与 Ratchet 关于"LLM 自写技能 +0.0pp"的判断，正是拿它的结果做对照得出的。

## 13. 横向结论（只讲和前三个问题相关的）

1. **优化对象的成熟度是倒挂的。** 大家先学会了改正文（单文档），再学改库（多技能），最后才敢碰元数据（`description`）和元流程——而 SkillReducer 的实证说明**最便宜、收益最直接的恰恰是被忽略的 `description`**（26.4% 的技能压根没有）。

2. **三种"控制哲学"，其实各管一个量。**
   - **接受门的严格度**（SkillOpt「严格大于才要」、SkillBoost「回归上限内才要」、VCE 沿用基础 evolver 的门）：管"新改动值不值得进"；
   - **淘汰边际 + 库宽上限**（Library Drift / Ratchet：`Nmin=100`、`τ=0.10`、`C=50`）：管"旧技能该不该走"；
   - **RL 惩罚**（SkillOS：无门控，靠复合奖励 + on-policy 采样）：管"策展策略本身该怎么学"。
   读论文时先认它属于哪一类，很多"为什么它这么设计"就自洽了。

3. **参数"更多"往往不等于更好**，这是这批工作最一致的经验结果：Best-of-N 从 4 加到 8 只多 2.5pp（理论上收益只有 `√lnN`）；外部经验条数 K 从 5 提到 7 掉 1.11–1.88 分；注意力步长 η 从 0.1 提到 0.2 掉 2.28–3.88 分；慢循环从 H=2 缩到 H=8 反而从 48.94 掉到 39.84。**瓶颈在信号质量，不在预算。**

4. **优化对象越往下走，评测就越像软件工程。** 改单份文档时只要 pass@1；管技能库时要 recall/precision（Repo2Skill-Evo）、grounding gate（引用能否在仓库解析）、form gate（结构非法直接 0 分）、NL judge 五维评分。**"能不能量"比"能不能改"更难。**

5. **场景决定收益量级。** MetaSkill-Evolve 在 OfficeQA 上 +23.54、ALFWorld 上只有 +1.92；SkillOpt 在 SpreadsheetBench 上 +38.9、SearchQA 上 +9.6。**不要跨任务外推增益。**

6. **只有一篇真的碰了"递归"**：MetaSkill-Evolve 同时进化 task skill 与 meta-skill（且只递归一层）。其余都在优化同一层的对象，区别只在优化器——文本学习率 / 组件归因 / 版本历史先验 / 有状态 evolver / 库治理。

7. **成本基本都被藏起来了**：Library Drift 100 轮 ≈ 1.45 万次 LLM 调用（墙钟 6.5h）；VCE 约 1.1M tokens（+10%）；EvoSkill v2 报的是"每提升一个点的美元成本"（$0.89 vs SkillOpt $1.27）。**报增益不报成本的结论，一律先怀疑。**
